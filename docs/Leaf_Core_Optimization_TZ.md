# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: ГЛУБОКАЯ ОПТИМИЗАЦИЯ LEAF CORE

## Главная задача

Провести максимально глубокую техническую оптимизацию существующего ядра Leaf для Minecraft Java Edition. Цель — превратить его в высокопроизводительное ядро для огромного сервера с большим количеством одновременно подключённых игроков.

Не ограничиваться стандартными настройками Paper/Leaf. Исследовать архитектуру Minecraft, Paper и Leaf, находить устаревшие, медленные и неэффективные реализации и заменять их современными, более производительными решениями.

Главный приоритет — производительность без потери функциональности, стабильности и совместимости с существующими плагинами.

## 1. Глубокая оптимизация исходного кода

Провести полный аудит исходного кода Leaf и его зависимостей.

- Находить медленные алгоритмы и неэффективные реализации.
- Переписывать неоптимизированный hardcoded-код на более быстрые алгоритмы.
- Оптимизировать часто вызываемые методы (hot paths).
- Сокращать лишние аллокации объектов.
- Уменьшать количество ненужных вычислений и копирований данных.
- Оптимизировать коллекции, циклы, структуры данных и алгоритмы поиска.
- Устранять избыточные блокировки и синхронизацию.
- Использовать современные возможности Java.
- Пересматривать устаревшие реализации Minecraft, которые можно заменить более эффективными аналогами.

Не заменять старые внутренние механизмы Minecraft без доказуемого выигрыша и проверки корректности.

## 2. Изучение архитектуры Folia

Изучить исходный код Folia и его архитектурные решения. Использовать подходы Folia как источник идей для оптимизации многопоточности Leaf.

Особое внимание:
- Region-based scheduling.
- Региональное владение игровыми данными.
- Асинхронное выполнение безопасных вычислений.
- Оптимизация передачи задач между потоками.
- Снижение нагрузки на Main Thread.
- Безопасная обработка сущностей и чанков.
- Уменьшение блокировок между потоками.

Переносить полезные архитектурные решения Folia только там, где это действительно оправдано. Не превращать Leaf в Folia автоматически и не ломать Bukkit/Paper API ради многопоточности.

## 3. Оптимизация основных подсистем Minecraft

Провести глубокую оптимизацию:
- Entity System и Entity Tracking.
- Chunk Loading и Chunk Generation.
- Block Ticking и Scheduled Ticks.
- Redstone и Block Entities.
- Pathfinding и Mob AI.
- Collision Detection.
- Lighting Engine.
- Network и Packet Processing.
- Region File I/O и сохранение мира.
- Player Management.
- Plugin Scheduler и Event System.

Для каждой подсистемы искать архитектурные ограничения, узкие места и возможности полной или частичной замены старых алгоритмов.

## 4. Client FPS Optimization

Разработать систему снижения клиентской нагрузки.

Основные направления:
- Оптимизация передачи обновлений блоков.
- Группировка и устранение дублирующихся Block Updates.
- Оптимизация массовых взрывов TNT.
- Уменьшение необязательных визуальных событий.
- Оптимизация передачи частиц.
- Оптимизация Entity Metadata и Entity Tracking.
- Оптимизация обновлений освещения.
- Интеллектуальное управление сетевыми очередями.
- Снижение количества избыточных пакетов.

Особенно важно обеспечить нормальную производительность клиентов при взрывах тысяч TNT, массовом разрушении блоков и большом количестве сущностей.

Не нарушать игровую механику и синхронизацию мира. Учитывать, что сервер не может напрямую управлять рендерингом и FPS клиента без клиентского мода; оптимизировать только те серверные и сетевые факторы, на которые он действительно влияет.

## 5. JVM и Garbage Collector

Исследовать возможность перехода с Adoptium Java на GraalVM.

Рассмотреть:
- GraalVM JDK.
- ZGC (Generational ZGC, если поддерживается выбранной версией JVM).
- Современные JVM-оптимизации.
- Оптимизированные параметры работы с памятью.

Изучить проект с дополнительными JVM-флагами:
https://github.com/MeowIce/meowice-flags

Проверить совместимость предложенных флагов с конкретной версией GraalVM и Minecraft.

Обязательно провести сравнительные тесты:
- Adoptium + G1GC.
- GraalVM + G1GC.
- GraalVM + ZGC.
- GraalVM + рекомендованные MeowIce flags.

Не считать ZGC автоматически лучшим решением. Сравнить пропускную способность, задержки GC, использование RAM, CPU и стабильность при длительной работе сервера.

Цель — уменьшить паузы сборщика мусора, избежать чрезмерного роста задержек и обеспечить стабильную производительность сервера при длительном аптайме. Помнить, что GC не исправляет утечки памяти.

## 6. Совместимость плагинов

Это одно из важнейших требований. Существующие Bukkit/Paper-плагины должны продолжать работать.

- Сохранять совместимость с Bukkit/Paper API.
- Не изменять публичные API без крайней необходимости.
- Проверять совместимость внутренних изменений с плагинами.
- Не выполнять небезопасные операции с игровым состоянием из фоновых потоков.
- Сохранять корректность событий, команд и планировщика.
- Не допускать изменения игровой механики.

При невозможности сохранить полную совместимость документировать конкретное ограничение и причину.

## 7. Производительность и тестирование

Каждое существенное изменение должно сопровождаться измерениями.

Использовать:
- Spark.
- JFR.
- async-profiler.
- JMH.
- GC Logs.

Проверять:
- TPS и MSPT.
- p95 и p99 времени тика.
- CPU Usage.
- RAM Usage.
- GC Pause Time.
- Количество аллокаций.
- Сетевой трафик.
- Производительность при массовых взрывах.
- Производительность при большом количестве игроков.
- Стабильность при длительном аптайме.

Сравнивать результаты с оригинальным Leaf на одинаковом оборудовании и при одинаковой нагрузке. Отдельно проверять клиентский FPS на одинаковых клиентах и настройках, если заявляется его улучшение.

## 8. Правила разработки

1. Сначала изучить весь проект и определить его архитектуру.
2. Определить наиболее проблемные участки кода.
3. Составить план оптимизации с приоритетами.
4. Не переписывать всё одновременно.
5. Вносить изменения небольшими логическими этапами.
6. После каждого этапа собирать ядро и запускать тесты.
7. Проверять корректность игровой механики.
8. Проверять совместимость плагинов.
9. Не удалять функциональность ради синтетических показателей производительности.
10. Не использовать небезопасную многопоточность.
11. Не выдавать предполагаемый прирост за измеренный.
12. Фиксировать изменения в отдельных Git-коммитах.
13. Сохранять возможность отката каждого изменения.
14. Не менять поведение по умолчанию без отдельного обоснования и тестирования.

Если обнаружена возможность заменить старую архитектуру более эффективной — исследовать её, подготовить новую реализацию и провести сравнительные тесты.

## 9. Конечная цель

Создать максимально производительный форк Leaf, способный обслуживать огромный онлайн с минимальными задержками и стабильным TPS.

Приоритеты:
1. Максимальная производительность игрового ядра.
2. Минимальный MSPT и стабильный TPS.
3. Эффективное использование доступных ресурсов CPU.
4. Эффективное использование многопоточности.
5. Минимизация задержек Garbage Collector.
6. Снижение нагрузки на клиентский FPS там, где это возможно со стороны сервера.
7. Стабильность при экстремальных игровых событиях.
8. Совместимость с Bukkit/Paper-плагинами.
9. Отсутствие потери игровых данных и функциональности.

**Главное требование:** не ограничиваться косметическими оптимизациями. Исследовать фундаментальные механизмы Minecraft и Leaf, заменять устаревшие решения современными алгоритмами и архитектурами там, где это безопасно и подтверждается реальными тестами.

Работать как инженер производительности JVM и Minecraft Core, а не как разработчик, который просто меняет настройки конфигурации.
