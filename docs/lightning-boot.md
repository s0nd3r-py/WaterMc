# Lightning-Boot: изменения 12 ноября 2026

DFU представлен LazyDataFixer: получение DataFixer и update без повышения DataVersion не строят схемы. Первое реальное преобразование или явный getSchema строит один экземпляр через JVM holder. Предварительная optimize-компиляция по умолчанию пропускается; watermc.eager-dfu=true оставляет её доступной. Регистрационная диагностическая проверка CHECK_DATA_FIXER_SCHEMA включается отдельно через watermc.check-dfu-schemas=true, иначе сам Bootstrap принудительно строил все схемы. Старые преобразования и schema API делегируются исходному Mojang DFU. Это перенос стоимости на первую конвертацию, а не измеренное сокращение времени запуска или RAM.

Переотображение плагинов (Spigot → Mojang) и преобразование байткода старых плагинов включены по умолчанию, как в Paper: плагины под Spigot работают без настройки. Кэш хранится в `plugins/.water-remapped`; кэш `plugins/.paper-remapped`, оставшийся от прежнего ядра, переносится туда при запуске и остаётся действительным.

Почему ремаппер не замедляет запуск:
- **Маппинги читаются лениво.** Файлы маппингов (десятки мегабайт) загружаются только при первом плагине, которому действительно нужно переотображение. Paper загружает их в фоне на каждом запуске. После включения плагинов маппинги освобождаются.
- **Classpath сервера в именах Spigot** строится тоже лениво и один раз на версию сервера, в несколько потоков.
- **Кэш хэшей jar** (`plugins/.water-remapped/hashes.tsv`). SHA-256 плагина считается один раз и переиспользуется, пока у файла не изменились размер и время изменения. Paper перечитывает каждый jar целиком на каждом запуске, а один и тот же jar — по нескольку раз за запуск. Отключение кэша: `-Dwatermc.remapper.trust-timestamps=false`.
- **Индекс** очищается за один проход и пишется на диск только при изменениях. Повреждённый индекс пересоздаётся и не мешает запуску.

Отключение ремаппера: `-Dwatermc.enable-legacy-remapper=false` или прежний флаг Paper `-Dpaper.disablePluginRemapping=true`.

В серверных Java-исходниках уже не было Timings hooks/classes. Существующие no-op Timings и CustomTimingsHandler в API сохранены. Не заявляется восстановление всех API-сигнатур из произвольных древних версий Paper.

Заменены четыре synchronized-wrapper: immutable serializer map используется напрямую, GameEvent cache использует immutable fastutil identity snapshots с сериализованным редким miss, EntityType cache — acquire/CAS ordinal array, TPS history — primitive ring с volatile mean. Среднее суммируется в прежнем хронологическом порядке, а не накопительной суммой с изменением округления. Два GUI Vector заменены ArrayList/массивами. Синхронизация действующего жизненного цикла сетевых соединений сохранена: там есть реальные Netty producers, это не мёртвые обёртки. Публичные Long timestamps старого TPSCalculator сохранены для совместимости; нулевые аллокации всего тика не заявляются.

В основном цикле уже применялся parkNanos и абсолютный deadline, а не Thread.sleep. TickWait добавляет coarse park и финальный spin (по умолчанию 50 мкс; watermc.tick-spin-nanos=0 отключает spin, максимум 500 мкс), сохраняя deadline и обработку очереди задач. Это не гарантия real-time точности ОС. Отдельный sleep при shutdown для отправки пакетов оставлен.

Тесты проверяют настоящий Minecraft Bootstrap без инициализации DFU, concurrent единственную загрузку схем, отказ от ASM по умолчанию, opt-in policy, identity/enum caches, побитовое совпадение среднего на 10 000 обновлениях и 0 байт после прогрева для history/cache-hit. Полный серверный startup/RAM benchmark на целевой машине не выполнен.

## Свой загрузчик (`me.s0nd3r.watermc.launcher`)

Загрузчик paperclip, унаследованный от Leaf (`cn.dreeam.leaper`), на каждом запуске перечитывал и хэшировал все распакованные библиотеки и сам сервер (~160 файлов, ≈125 МБ). Только после этого стартовал сервер.

Загрузчик WaterMc:
- работает с тем же форматом jar и теми же каталогами `versions/` и `libraries/`;
- хранит в `libraries/.watermc-launcher` размер, время изменения и SHA-256 каждого проверенного файла;
- не перечитывает файл, у которого совпали размер и время изменения, а ожидаемый хэш в jar не изменился;
- проверяет изменённый, повреждённый или отсутствующий файл как раньше и при необходимости распаковывает его заново, в несколько потоков;
- поддерживает свойства `bundlerRepoDir`, `bundlerMainClass`, `paperclip.patchonly`;
- проверяет каждый файл на каждом запуске с флагом `-Dwatermc.launcher.verify-all=true`;
- скомпилирован для Java 8: на старой Java выводит понятное сообщение «нужна Java 21».

Замер на одной и той же тёплой папке, время до запуска main-класса ядра:

| | Время |
|---|---|
| Загрузчик Leaf | 3,8–4,4 с |
| Загрузчик WaterMc | **0,7–0,8 с** |

Первый запуск нового загрузчика один раз проверяет все файлы и записывает отметки.

## Маппинги Spigot↔Mojang (`ObfHelper`) только по необходимости

Paper разбирал файл маппингов на каждом запуске «для расшифровки stacktrace». WaterMc работает в именах Mojang, и stacktrace уже читаемые. Таблица нужна только Bukkit-плагинам, собранным под Spigot, для перевода их reflection-вызовов.
- Нет таких плагинов — таблица не загружается: 0 классов против 46 у прежней сборки, нет разбора файла и нет таблицы в памяти.
- Есть — таблица загружается в фоновом потоке с низким приоритетом после загрузки плагинов, без паузы при первом обращении.

## Плагины «только API» не переотображаются

Если ни один класс плагина не ссылается на `net/minecraft/`, `com/mojang/` или `org/bukkit/craftbukkit/`, переотображать в нём нечего. Плагин запускается как есть, без построения classpath сервера в именах Spigot (около 10 с один раз на версию) и без перепаковки jar. Отметка о маппингах в манифесте на загрузку классов не влияет: reflection и старые API обрабатываются при загрузке одинаково для всех плагинов.

Проверка консервативная: искомые байты ищутся по всему `.class`, включая строки. При ошибке чтения плагин переотображается как раньше.
- Отключение: `-Dwatermc.remapper.skip-api-only=false`.
- Живая проверка: тестовый плагин WaterBench распознан как «только API» и запущен без переотображения.

## Что проверено и отклонено

- **AppCDS** (архив классов JVM). Архив работает и с нашим загрузчиком: 14 540 классов взяты из архива. Но время запуска не изменилось в пределах шума (34,5 против 35,6 с, 37,2 против 35,8 с), потому что время уходит на статическую инициализацию реестров, а не на чтение классов. Не включено и не рекомендуется.
- **xxHash вместо SHA-256 в ремаппере.** После кэша хэшей SHA-256 считается только для изменившихся jar, так что выигрыша нет.
