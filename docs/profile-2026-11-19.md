# Профилирование и правки по профилю (19 ноября 2026)

## Как снимался профиль

- Стенд `benchmarks/run-native.py`, сцена `entities:1500:120,chunkgen:12`: 1500 мобов (коровы, овцы, свиньи, куры, жители, зомби, скелеты, железные големы, волки) с AI, коллизиями и трекингом, затем генерация 625 чанков. Два бота, heap 4 ГБ, Java 21.
- JFR с профилем `profile` пишется 150 с с начала измерения. Анализ: `benchmarks/tools/jfr_hotspots.py`.
- Прогоны фоновые, с пониженным приоритетом, на рабочей машине (AMD FX-4100). Поэтому сравниваются **доли методов внутри профиля**, а не абсолютные MSPT между прогонами.

Каталоги прогонов: `D:/water-mc/run/profile-watermc-entities-1` (до правок), `profile-watermc-entities-2` (после). Сводки: `benchmarks/results/2026-11-19-native/`.

## Найденные ошибки

1. **Игроков отключало при отправке крупных пакетов.** Общий кэш сжатых пакетов хэшировал direct-буфер библиотекой zero-allocation-hashing. Ей нужен доступ к `sun.nio.ch.DirectBuffer`, а без флага `--add-exports` она бросала `IllegalAccessError` в Netty-энкодере. При обычном `java -jar` это отключало игрока на первом чанке.
   - **Исправление:** хэш через `CRC32C` (штатная поддержка direct-буферов, процессорный интринсик). Делиться пакетом по-прежнему разрешает только побайтовое сравнение.
   - **Проверка:** регрессионный тест в обычной тестовой JVM без флагов; во втором прогоне оба бота оставались подключены и получили 5,18 млн пакетов.
2. **Длинный тик (6,4 с) при очистке тикетов** после сценария в первом прогоне совпал с отключением ботов. Во втором прогоне максимальный тик на фазе сущностей — 2,9 с (это первый тик массового спавна), на фазе генерации — 128 мс. Повтора нет.

## Правки по профилю

Основной тиковый поток (95% CPU процесса), доля в сэмплах:

| Метод | До | После | Что сделано |
|---|---|---|---|
| `LivingEntity.getHealth` (собственное) | 4,28% | 0,00% | Здоровье хранится в обычном поле `float`, которое обновляется после каждой записи `DATA_HEALTH_ID`: конструктор, `setHealth`, `CraftPlayer`, обратный вызов синхронизации. Раньше каждый `isAlive()` в проверке целей проходил цепочку entity → массив данных → элемент → упакованный `Float` |
| `LivingEntity.isAlive` (полное) | 4,41% | 0,85% | следствие правки выше |
| `Objects.checkIndex` из `WaterSectionStorage.get` | 2,27% | 0,00% | Убрана лишняя явная проверка границ: доступ через `VarHandle` к массиву сам проверяет границы. В компактном состоянии проверка осталась. Тест на выход за границы в обоих состояниях |
| `Profiler.get` (полное) | 3,00% | 0,00% | Каждый тик сервер регистрировал заведомо неактивный профайлер. Из-за этого каждый `Profiler.get()` весь тик ходил в `ThreadLocal` за тем же `InactiveProfiler`. Неактивный профайлер больше не регистрируется, `/debug` и `/perf` работают как раньше (тест) |

Итого около 9% времени основного потока в этой сцене. Абсолютный выигрыш MSPT на целевом сервере нужно подтверждать контролируемым прогоном.

## Память под чанки: замер и исправление

Один и тот же сохранённый мир (обычный рельеф, сид 20261119, 1024 форсированных чанка, всего 1600 загруженных) запущен в исходном Leaf и в WaterMc с одинаковыми JVM (Java 21, G1, куча 4 ГБ). Через 90 секунд после старта снималась `jcmd GC.class_histogram` (перед подсчётом выполняется полная сборка). Скрипт: `benchmarks/tools/chunk_memory.py`; каталоги `D:/water-mc/run/chunkmem-*`.

| | Leaf | WaterMc до | WaterMc после |
|---|---|---|---|
| Живая куча после полной сборки | 393,2 МиБ | 832,7 МиБ | **385,2 МиБ** |
| На один загруженный чанк | 251,6 КиБ | 532,9 КиБ | **246,5 КиБ** |
| `long[]` (данные секций) | 46,6 МиБ | 495,9 МиБ | 46,6 МиБ |

**Причина.** С прошлых этапов все неоднородные секции блоков хранились в плоском `WaterSectionStorage` (`long[4096]`, 32 КиБ). В Paper и Leaf используется упакованное хранилище: 4–8 бит на блок, 2–4 КиБ на секцию. Для сервера с 10–20 тыс. загруженных чанков это давало бы лишние 3–5 ГБ кучи.

**Исправление.** По умолчанию снова используется упакованное хранилище. Плоское доступно опцией `-Dwatermc.flat-section-storage=true`. Тест фиксирует, что по умолчанию хранилище упакованное; тесты плоского режима сохранены. Полный прогон: upstream 8951, тесты WaterMc 181, совместимость 26 — без ошибок.

Теперь WaterMc держит в памяти на 8 МиБ (2%) меньше, чем Leaf, на том же мире, в основном за счёт ленивого DataFixerUpper.

### CPU после возврата упакованного хранилища

Повторный прогон той же сцены (`profile-watermc-entities-3`, 1500 мобов, 2 бота, JFR 150 с). Доли основного потока:

| | Плоское (прогон 2) | Упакованное (прогон 3) |
|---|---|---|
| Чтение из секции (контейнер + хранилище + палитра) | 5,23% | 0,85% |
| Поиск чанка `ChunkCache.get` | 8,02% | 11,87% |
| **Чтение блока целиком** | **13,25%** | **12,72%** |
| Поиск пути `WalkNodeEvaluator.getNeighbors` (полное) | 6,99% | 6,84% |
| `Entity.move` (полное) | 6,34% | 7,06% |

Стоимость чтения блока не выросла, а перераспределилась: плотное хранилище лучше ложится в кэш процессора, и ожидание памяти атрибутируется соседнему вызову. По CPU разница в пределах погрешности, по памяти — вдвое меньше. MSPT прогонов (фоновые, пониженный приоритет): 50,9 мс и 49,8 мс — в пределах шума. Сравнение абсолютных цифр между фоновыми прогонами некорректно.

Следующие цели по этому профилю: поиск соседних сущностей (`EntityCollectionBySection.getEntities`, 13%) и поиск чанка на каждое чтение блока (`ChunkCache.get`, около 12%). Для поиска чанка нужен замер средней длины пробирования на живом сервере: построчная атрибуция JFR внутри цикла ненадёжна из-за смещения сэмплов к точкам safepoint.

## Поиск соседних сущностей

### Сцена и ложный след

Сцена `crowd:600:60:6:0` — 600 коров в загоне 13×13 блоков, давка выключена, ботов нет. В первых профилях треть основного потока приходилась на `String.hashCode` из `Scoreboard.getPlayersTeam` (поиск команды соседа в предикате толкания). Повтор с `-XX:+DebugNonSafepoints`, который даёт точную привязку сэмплов к встроенным методам, показал другое: поиск команды занимает 1,2%, а `String.hashCode` — 0,4%. Остальное — сам перебор сущностей секции (`EntityCollectionBySection.getEntities`, 24% собственного времени).

**Вывод для дальнейших замеров:** профили сцен со встраиванием снимаются только с `-XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints`.

### Причина

Для каждой сущности в секции проверка пересечения шла по цепочке «массив → объект сущности → объект `AABB` → поля»: два промаха кэша на кандидата. 600 коров в одной-двух секциях дают около 360 тысяч таких проверок за тик.

### Исправление

- **Плоская копия габаритов.** Список сущностей секции (`allEntities`) хранит рядом с массивом сущностей `double[]` по 6 чисел на сущность. Копия обновляется в `Entity.setBoundingBox` (единственное место записи `Entity.bb`) через номер сущности в списке. При удалении номер переносится вместе с последним элементом. Проверка пересечения читает подряд идущие числа; объект сущности затрагивается только при совпадении. Сравнения те же, значения те же (тест: 500 000 случаев против `AABB.intersects`, включая касание граней).
  - Отключение: `-Dwatermc.packed-entity-bounds=false`.
  - Самопроверка: `-Dwatermc.packed-entity-bounds.verify=true` сверяет копию с настоящими габаритами при каждой проверке.
- **Команда не-игровой сущности.** `Scoreboard` считает записи команд с ключом длины UUID (36 символов; имена игроков не длиннее 16). Пока их нет, `Entity.getTeam()` у не-игрока сразу возвращает `null`, не трогая строку UUID. Тест: 50 000 случайных операций с командами, счётчик совпадает с содержимым.
- **Урезанный поиск для толкания** (`PushQuery`) оставлен: эквивалентность подтверждена дифференциальным тестом. Отдельного выигрыша он не дал: разница в пределах шума. Отключение: `-Dwatermc.limited-push-query=false`.

| Прогон | Тиков | Расхождений копии |
|---|---|---|
| Толпа 600 коров, давка 24, самопроверка | 1200 | 0 |
| 1500 мобов девяти видов, 2 бота, самопроверка | 1800 | 0 |

### Результат (A/B в одном JAR, прогоны чередовались при одинаковой нагрузке)

Доли основного потока, сцена толпы, давка 0:

| | Без копии (1) | Без копии (2) | С копией (1) | С копией (2) |
|---|---|---|---|---|
| Перебор сущностей секции, собственное | 16,6% | 17,8% | 2,2% | 2,8% |
| `LivingEntity.pushEntities`, полное | 21,2% | 25,3% | 11,1% | 10,0% |
| `Entity.getTeam`, полное | 1,3–1,8% (прогоны до правки) | | 0,4–0,6% | |
| MSPT (фоновые прогоны, не для сравнения) | 99,7 | 88,1 | 79,1 | 60,8 |

Толкание в толпе стало вдвое дешевле. Самое дорогое теперь — сам предикат толкания (`pushableBy`, 7%): он первым обращается к объекту каждой совпавшей сущности, а в плотной толпе совпадают почти все.

**Ограничения:**
- Машина во время прогонов была занята посторонними программами: процессу сервера доставалось 11–18% CPU против 39% утром. Абсолютные MSPT этих прогонов не сравнимы с утренними и между собой.
- Сравнение долей в смешанной сцене 1500 мобов с утренним профилем тоже некорректно: при чужой нагрузке на кэш процессора код, упирающийся в память, теряет больше остального.
- Копию ведёт только общий список `allEntities`. Поиски по классу и типу (`getEntitiesOfClass` для поиска целей) идут по своим спискам без копии. Это следующий шаг, но там сущность состоит в нескольких списках сразу, и одного номера на сущность уже недостаточно.

## Вечерний этап: поиск по классу, кэш чанков, ремаппер, консоль

### Плоская копия габаритов во всех списках секции

Копию теперь ведут все списки секции: общий, «жёстких» коллизий, по типу и по каждому запрошенному классу (`getEntitiesOfClass` — поиск целей мобами). Сущность состоит в нескольких списках, поэтому у неё таблица связей «список → номер» (`EntityBoundsLinks`, обычно 2–5 записей). `setBoundingBox` обновляет все копии. Временная секция при слиянии сначала покидается, затем сущность добавляется в новую, поэтому устаревших связей не остаётся.

Проверка: дифференциальный тест связей (100 000 операций), живой прогон «1500 мобов, 2 бота, 1200 тиков» с самопроверкой — 0 расхождений.

### Кэш соседних чанков

`ChunkCache.get` хранил один последний чанк. Поиск пути и коллизии у границы чанков чередуют до четырёх соседних чанков и постоянно промахивались мимо него. Теперь кэш на четыре ячейки по чётности координат: четыре чанка вокруг угла не вытесняют друг друга. Дифференциальный тест: 300 000 операций против `HashMap`. Отключение: `-Dwatermc.chunk-cache-neighbourhood=false`. Выигрыш в MSPT отдельно не измерялся.

### Ремаппер плагинов

Включён по умолчанию, как в Paper. Кэш — `plugins/.water-remapped`; кэш `.paper-remapped` от прежнего ядра переносится при запуске.

| | Paper | WaterMc |
|---|---|---|
| Маппинги на запуске, когда все плагины уже в кэше | читаются и разбираются в фоне | не читаются |
| SHA-256 плагинов | каждый jar целиком, на каждом запуске, по нескольку раз | один раз; после перезапуска — только изменённые jar |
| Classpath сервера в именах Spigot | при смене версии, на первом же запуске | только когда плагину нужно переотображение, в несколько потоков |
| Маппинги после включения плагинов | ссылка на прямые остаётся | освобождаются |

Живая проверка (`round-live-1`):
- Первый запуск с плагином без пространства имён: classpath собран за 9,9 с (один раз на версию сервера), сам плагин переотображён за 1,4 с.
- Повторный запуск того же сервера: переотображения нет, маппинги не загружались.

### Язык консоли

Настройка: `misc.console.language: en | ru | uk` в `watermc.yml` или `-Dwatermc.console.language`.
- Переводится только терминал: `logs/latest.log` остаётся на английском.
- Строка `Done (…)! For help, type "help"` не переводится: по ней панели хостинга определяют запуск.
- В таблицах больше ста сообщений: запуск, остановка, сохранение, игроки, предупреждения безопасности, сообщения WaterMc.
- Собственные сообщения WaterMc, раньше выводившиеся по-русски даже в английском режиме, переписаны на английский как базовый язык.

Живая проверка: запуск на русском и на украинском. Лишний перевод чужой строки (`Disabling …` от oshi) найден и исправлен: шаблоны плагинов теперь `Enabling {} v{}`. Тест закрепляет, что такие строки не переводятся.

### Скрипты

Новые события: `player_command`, `damage`, `interact`, `kill`, `world_change`. Событие `chat` теперь отменяемое: поток чата ждёт обработчик в основном потоке до 1 с. Тест нашёл конфликт: `command` — ключевое слово языка, поэтому событие называется `player_command`.

### Не сделано

- Heap guard по-прежнему чистит только кэши, а не чанки. Ранняя выгрузка чанков, удерживаемых отложенными тикетами игроков, требует менять логику тикетов (идентификатор игрока, уровень). Это отложено, пока нет живой проверки.
- Строка `No key layers in MapLike[{}]` (ERROR при создании мира) не исследована.

## Запуск: WaterMc против Leaf (19 ноября 2026, вечер)

Плоский мир, без плагинов, куча 2 ГБ, Java 21, одна машина. Скрипт: `benchmarks/tools/startup_compare.py`.

| Тёплый перезапуск (3 раза, поочерёдно) | WaterMc | Leaf |
|---|---|---|
| Время до `Done` | **27,1 с** | 28,9 с |
| Heap после запуска и GC | **214 МиБ** | 224 МиБ |

Это сборка до своего загрузчика и ленивых маппингов `ObfHelper`. Они дают ещё около 3 с (загрузчик) и около 1 с CPU плюс память таблицы маппингов. Повторить сравнение с ними на спокойной машине не удалось: во время последних прогонов посторонняя нагрузка держала CPU на 71–82%, и обе сборки стартовали по ~118 с.

**Первый запуск** в новой папке (распаковка, создание мира) зависит от того, кто запускается первым: холодный дисковый кэш.
- WaterMc первым: WaterMc 84,9 с, Leaf 46,5 с.
- Leaf первым: Leaf 70,2 с, WaterMc 43,1 с.

На втором месте WaterMc 43,1 с против 46,5 с у Leaf. Надёжного вывода о первом запуске из этих двух пар нет.

Хронология тёплого запуска: около 13 с — статическая инициализация ванильных реестров (≈13 тысяч классов: блоки, предметы, сущности), 5–7 с — датапаки, рецепты и теги, остальное — миры и сеть. Это унаследованный код Minecraft; следующий шаг — профилировать инициализацию реестров на спокойной машине.
