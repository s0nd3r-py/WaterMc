# Проверки WaterMc

Для обычной сборки сервера Node/Python/JMH не нужны. `.\build.ps1 -Verify` собирает сервер, запускает регрессионные и унаследованные проверки и создаёт WaterBench.

## Живые сценарии

`run-native.py` создаёт новый каталог, использует указанный JAR и тестовый плагин, выбирает свободный порт на 127.0.0.1 и сохраняет команды, SHA-256 JAR/плагина, версии клиентских библиотек, логи, CSV и пакеты. Старые каталоги и результаты не перезаписываются. `run-bench.sh` передаёт работу этому же стенду и больше не удаляет миры.

Нужен шаблон `<root>/base` с тестовыми конфигами, каталогом plugins и настройками запуска сервера. На этой машине используется существующий `D:/water-mc/run/base`. Можно передать свои `--root`, `--template`, `--seed-cache`, `--node-modules`, `--results-root`. Шаблон должен содержать согласованную начальную конфигурацию; случайные старые тестовые миры в него не добавляйте.

Клиенты требуют Node 22+. Зависимости закреплены в `bots/package-lock.json`: `npm ci --prefix benchmarks/bots`. На этом компьютере уже установленные пакеты находятся в `D:/water-mc/bench/bots/node_modules`; при установке новых используйте кэш на D:, например `--cache D:/water-mc/npm-cache`.

Пример фоновой функциональной проверки из корня репозитория:

```text
python benchmarks/run-native.py functional-new-label --jar watermc-server/build/libs/watermc-1.21.11.jar --java /path/to/jdk/bin/java --plugin benchmarks/waterbench/build/libs/waterbench-1.0.0.jar --spec compat:1,explosionpackets:1,particles:3:200 --bots 2 --heap 2G --functional-only
```

В Windows заключайте пути с пробелами в кавычки. `functional_only` означает пониженный приоритет и отсутствие выводов о скорости из MSPT/CPU/GC. Тестовый watchdog 300 секунд и увеличенный keepalive применяются только к свежему функциональному окружению. Производственные значения не меняются.

## Что проверяют сценарии

| Сценарий | Содержание |
| --- | --- |
| compat | FIFO/отмена/повтор задач, приоритеты/отмена событий, редстоун, запланированные тики жидкости, свет, воронка, путь моба, пространственный запрос, save/unload/reload, UUID сущности, PDC сундука и сохранённые тики |
| explosionpackets | На WaterMc напрямую вызывает внутренний лимитер и сверяет принятые клиентами порядок и векторы; урон и мир этим сценарием не меняются |
| particles:секунды:рассылки | Обычные NMS-частицы и исключения API/forced/always-show/vibration/targeted, реальное здоровье при масштабе 40 |
| tntburst:повторы:количество | Массовые одновременные TNT |
| entities:количество:игровые-секунды | Исходный сценарий смеси мобов с AI, коллизиями и tracking |
| chunkgen:радиус | Генерация только в новом тестовом мире; ошибочный future не считается успехом |
| soak:количество:реальные-секунды | Постоянное число неуязвимых мобов с AI; проверка численности, фактических тиков и реальной длительности |

Для длительного фона: `--spec soak:40:3600 --jfr-seconds 120 --timeout 7200`. Это час реального времени после прогрева; число игровых тиков сохраняется отдельно. Успех такого теста не доказывает стабильность многодневного рабочего сервера или онлайна 100.

JFR запускается через jcmd только на PID созданного стендом сервера после начала измеряемой нагрузки. Запись и команда сохраняются. Spark уже включён в ядро; локально он сообщил, что async-profiler не поддерживает Windows/amd64 и использовал Java-движок. Для async-profiler нужен отдельный поддерживаемый стенд. [JMH-микротест](micro/README.md) находится отдельно.

## Достоверность пакетов и GC

Клиенты считают декодированные payload, без TCP-обрамления и компрессии. Новая версия получает системные метки START/END каждой фазы и подтверждает END через plugin message. Сервер ждёт всех подтверждений перед следующей фазой и завершением. Сверяются номера фаз, отсутствие ранних ошибок транспорта, все ожидаемые частицы и тестовые векторы взрывов. Прогон с неполными границами или счётом отклоняется, логи сохраняются.

Фазовая статистика включает прогрев сценария; синтетические частицы отправляются после прогрева. Общая статистика старых версий счётчика не имела этих границ, поэтому их ограничения отмечаются отдельно.

Сводка GC из JMX охватывает сценарий вместе с прогревом; сырые GC-логи охватывают весь процесс. Для сравнения пауз нужно выбирать одинаковые интервалы по маркерам и журналам. Поздние JMX-уведомления предыдущего сценария отсечены отдельным поколением записи. Фоновые результаты не используются для выбора «лучшего GC».

`run-native-matrix.py` — последовательная матрица для текущей локальной установки JVM. Пять наборов флагов и их ограничения описаны в `../docs/jvm-guide.md`. На другом сервере передавайте его пути и фактическую конфигурацию через общий драйвер.
